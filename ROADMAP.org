#+title: closure — capability roadmap
#+todo: TODO(t) WIP(w) | DONE(d) DROP(x)

Working agreement for autonomous sessions: work top-down, pick the
highest =TODO=, split it into small TDD cycles, flip it to =DONE= in the
same commit that finishes it. Every item must pass the test "after this
the user can ___, which they could not before" — if the blank only
names a new method, the item does not belong here. Statistics/alias
accessor methods on closure-org/store/input are done; add no more
unless a feature in the same cycle calls one. Architecture contract
lives in [[file:docs/spec.md][spec.md]] (invariants I1–I10) and [[file:docs/phases.md][phases.md]] (milestones); this
file is the fine-grained, capability-level queue between them. Blocked
on a design decision? Record it under [[*Decisions][Decisions]], pick the most
reversible option, keep moving.

* WIP GUI-PARITY — every GUI shell a real interactive editor [6/7]
GUI-UX brought the hermetic cores to parity (every shell consumes
=App=/=Shell= + renders the =ViewTree=); the gap left is the windowed
=run()= loops — gpui/egui edit live, gtk/qt render a static snapshot,
tauri hosts the read-only export. Parity = ONE tested input→command→Shell→
=ViewTree= dispatch every window delegates to; the only per-shell code is
event translation + paint. Binding rules (same as GUI-UX): strict 7-step
TDD, one leaf per pass, never weaken a test or lower a gate (coverage floor
>=84), each leaf revises =docs/spec.md= + a dated Decision in the SAME
commit, non-hermetic window deps feature-gated OFF with =just check= green
(I10); the window is build-verified under the right devShell + manual smoke.

** DONE P1 Unified input/event dispatch [1/1]
=KeyEvent { key, ctrl, text }= (constructors =key=/=ctrl=/=char=) +
=App::dispatch(&mut Shell, &KeyEvent) -> Node= are the single step every
shell's window calls: apply the event via the mode-aware =on_key= (mutating
through the registry, I8), return the refreshed =ViewTree=. =on_key= itself
gained a doc as the low-level handler behind =dispatch=. Proven headlessly
in =tests/dispatch.rs=: a full =C-c=, type, =enter= capture round-trip
driven through =dispatch= alone shows the new headline in the returned
=ViewTree= AND persists to disk; =C-q= quits via the same path; escaping
every editing surface never panics (I5). =just check= 3564 green.
*** Decision (2026-06-28) Event in, ViewTree out — one call, not three args.
=on_key= already existed (the gpui core), but shells called it then
separately re-read =view=. =dispatch= fuses the two into the parity
primitive: a window translates its native event into =KeyEvent= and gets
back the tree to paint — nothing else. Wrapping the loose =(key, ctrl,
text)= in a typed =KeyEvent= gives every shell the same constructors and
keeps the per-shell adapter to "native event → KeyEvent" + "paint Node".
The behaviour stays in =on_key= (untouched, still tested), so P1 is the
seam, not a rewrite; P2–P4 wire each window onto it.

** DONE P2 GTK interactive editor loop [1/1]
The GTK window went from a static snapshot to a live editor. =next_frame(
&mut App, &mut Shell, &KeyEvent) -> String= is the hermetic seam — dispatch
(P1) + =widget_tree= — the exact step the window runs per keypress; tested
in =tests/interactive.rs= (a =C-c=/type/=enter= capture driven through
=next_frame= edits the vault + rebuilds the widget tree + persists; nav
changes the frame). The feature-gated =run= now holds =Rc<RefCell<(App,
Shell)>>=, attaches an =EventControllerKey= that maps each GDK key (+Ctrl)
to a =KeyEvent= via =gdk_key_to_event=, calls =next_frame=, and repaints the
=ListBox=. Default =just check= 3566 green (feature OFF); =--features gtk=
build-verified under =.#webview=.
*** Decision (2026-06-28) The window shares next_frame, not a parallel loop.
The interactive =run= and the hermetic test call the SAME =next_frame=, so
"what the window paints each key" is exactly what the test asserts — the
display-bound part shrinks to GDK→KeyEvent translation + =ListBox= repaint.
The =ViewTree=→widget mapping is still a descriptor string (one =Label= per
line) rather than a structural widget build; that keeps =next_frame= pure +
golden-able. A richer structural build (real nested boxes) is a later
refinement that can't change the tested seam, so it's not a parity gap.

** DONE P3 Qt6/QML interactive editor loop [1/1]
The Qt window mirrors P2. =next_frame(&mut App, &mut Shell, &KeyEvent) ->
String= (dispatch + =qml_view=) is the hermetic seam, tested in
=tests/interactive.rs= (a =C-c=/type/=enter= capture driven through it
edits the vault + rebuilds the QML + persists; nav changes the frame). The
feature-gated =run= builds a =Bridge= =QObject= (=qmetaobject=) exposing an
=on_key= invokable + a =frame= =qt_property=; the host QML routes
=Keys.onPressed= (special keys by name, printable by =event.text=, Ctrl via
modifiers) to =bridge.on_key=, which runs =next_frame= and republishes
=frame= (NOTIFY-bound, so the view updates live). Default =just check= 3568
green (feature OFF); =--features qt= build-verified under =.#webview=.
*** Decision (2026-06-28) A QObject bridge, frame as a NOTIFY property.
Qt has no =EventControllerKey= equivalent reachable from pure Rust, so the
interactive seam is a =qmetaobject= =QObject=: QML owns the key routing and
calls back into Rust =on_key=, which drives the SAME =next_frame= the test
asserts. The fresh document rides a =qt_property!(QString; NOTIFY)= so QML
re-renders on change with no engine reload. The qmetaobject derive forces a
glob import + owned-=QString= method args + post-=Default= field assignment
— scoped to a =#[cfg(feature="qt")]= module with a documented =allow=, so
the default build (and =just check=) never sees them. Showing the
regenerated document live (vs nesting it as re-instantiated QML) is the
display-bound refinement, not a parity gap.

** DONE P4 Tauri/web interactive parity [1/1]
The Tauri window went from hosting the read-only =export_html= snapshot to
hosting the LIVE editor. =interactive_page(vault) -> String= is the
hermetic seam — the web shell's served root page (=respond(GET "/")=) with
its =POST /capture= form + fuzzy search, the surface whose form round-trips
to the registry (I8). Tested in =tests/interactive.rs=: the live page
carries the =<form action="/capture">= and differs from the static export.
The feature-gated =run= now spawns =closure_shell_web::serve= on
=SERVE_ADDR= (=127.0.0.1:8787=) in a thread and loads =http://…/= via
=wry= =with_url=, so the webview's captures persist through =Vault::capture=.
Default =just check= 3570 green; =--features tauri= build-verified under
=.#webview=.
*** Decision (2026-06-28) Host the served page, don't re-bridge via IPC.
The web shell already had a tested interactive surface (=respond= +
=serve=, =POST /capture= → =Vault::capture=); the honest parity move is to
*host* it, not invent a second wry-IPC mutation path. =run= serves on
localhost and loads the URL, so the capture form already works end-to-end
through the registry — the same I8 path the CLI/TUI use. =interactive_page=
makes "tauri hosts the live editor (not the export)" a hermetic fact (form
present, differs from export); the server+window are display/network-bound
and build-verified. A fixed localhost port keeps it dependency-free; an
ephemeral port + handshake is a later refinement, not a parity gap.

** DONE P5 Theme applied in every window [1/1]
The two newly-interactive native windows now apply the shared =Theme=
tokens. =closure_shell_gtk::theme_css(&Theme)= maps the palette to a GTK4
CSS string (=window=/=label= colours + =.selected=/=.toast-*= classes); the
window loads it into a =CssProvider= via
=style_context_add_provider_for_display=. =closure_shell_qt::theme_qml(
&Theme)= maps it to QML =readonly property color= decls (bg/fg/accent); the
host document binds the window =color= + text colour. Both mappings are
hermetic (tested: palette hex present, themes differ, high-contrast is
black/white). Default =just check= 3574 green; =--features gtk= /
=--features qt= build-verified under =.#webview=.
*** Decision (2026-06-28) Per-shell token→native mapping, one palette.
Theme stays the single typed source (G2); each shell owns only the tiny
map to its native styling vocabulary — CSS for GTK, =property color= for
QML, =Color::Rgb= for tui (G2), CSS vars for web (G2), and
=Theme::color().rgb()= for gpui/egui. So a colour change is one palette
edit, not five. The mapping functions are pure + golden-tested; loading the
=CssProvider= / binding the QML props is the display-bound apply. The window
defaults to the dark theme; resolving =config.theme= per window (via
=Theme::from_name=) is a thin wire-up, not a parity gap — recorded.

** DONE P6 Feedback + interaction states in every window [1/1]
=with_feedback(base, &Feedback) -> Node= composes the typed feedback queue
onto a =ViewTree= as =Node::Toast= nodes — appended to a =Pane='s children,
or wrapping any other node — so notifications + progress reach every window
from the one shared queue (every shell already renders =Toast=, G1c/G8;
empty feedback is a no-op). =ElementState::class= is the stable paint token
(=normal=/=hovered=/=focused=/=active=/=disabled=) each shell maps to its
native focus-ring / hover / dimming. Tests: toasts (notify + progress)
appear in the composed tree's JSON + snapshot, original content survives,
empty is unchanged, classes are distinct. =just check= 3578 green.
*** Decision (2026-06-28) Reuse the Toast vocabulary, don't re-plumb per shell.
Feedback already lowers to =Node::Toast= (G7), and every renderer already
draws =Toast= (G1c, proven by the G8 harness) — so "feedback in every
window" is just composing the queue onto the view (=with_feedback=), not new
per-shell notification code. Likewise =ElementState= stays a shared machine
(G5b); P6 only adds its =class= token so each shell maps one string to a
native style, rather than each inventing focus/hover logic. Binding the
class onto specific rows + animating toasts are display-bound, not parity
gaps; the state + composition are the tested part.

* DONE GUI-UX — every GUI shell a full-blown, top-notch editor [9/9]
The GUI tier is uneven: gpui/egui are full editors, tauri hosts the web
shell, but gtk/qt are read-only headline lists, and "great UX" exists
nowhere as *tested* structure. Pixels can't be gated hermetically
(window-bound), so depth lives in the shell-core state + the declarative
=ViewTree=; the native window stays a thin display-bound adapter. Each
leaf's PROOF is a headless ViewTree/state assertion + golden snapshot;
the window is build-verified + manual smoke (gpui/egui class). Binding
rules (same as Depth IV): strict 7-step TDD, one leaf per pass, never
weaken a test or lower a gate (coverage floor stays >=84), each leaf
revises =docs/spec.md= + adds a dated Decision in the SAME commit,
non-hermetic window deps feature-gated OFF with =just check= green (I10).

** DONE G1 Rich ViewTree vocabulary: splits / overlays / notifications [3/3]
The =Node= enum described a single screen; a "full-blown editor" needs a
richer, still-declarative layout vocabulary. G1 grows it one kind per
sub-cycle, each exhaustively matched across every renderer (V1c), so a
shell that omits one does not compile.
*** DONE G1a =Node::Split= — multi-pane layout
=Node::Split { direction: SplitDir, panes }= arranges child panes along a
=Row=/=Column= axis — the foundation for sidebar + main + detail. Wired
through =kind=/=aria_role= (group)/=view_to_json=/=serialize_view= in
closure-shell-core and both =render_view= embedders (=closure-tui= text,
=closure-shell-web= flex =div=); =ALL_NODE_KINDS= 8→9, =split_node=
constructor. Hermetic proof: panes render in order, the axis is labelled
(=split:row= / =class="split split-row"=), JSON nests panes — golden in
=rich_view.rs= (shell-core/tui/web). En route, the D9 =tables= proptest
surfaced a real I5 panic — list-item checkbox scan sliced =&after_ws[..1]=
mid-codepoint on input =-\t<3-byte char>=; fixed to byte comparison
(markers are ASCII) + a pinned regression test. =just check= 3501 green.
*** Decision (2026-06-28) Add kinds, never a =_= wildcard in renderers.
The rich vocabulary lands as new =Node= variants, not flags on existing
ones, precisely so the exhaustive =match= in every renderer breaks at
compile time until each shell handles the kind (the V1c guarantee is the
whole point — it forces cross-shell parity). =Split= carries only
structure (axis + ordered panes); how wide each pane draws is the
embedder's pixel job, outside the hermetic gate. =SplitDir= is a tiny
=Copy= enum with a stable =as_str= tag so JSON/CSS stay deterministic.
*** DONE G1b =Node::Modal= — overlay layer (palette/dialog over a base)
=Node::Modal { title, body: Box<Node> }= is a titled overlay floating
above the base surface — the command palette, a confirm dialog, a prompt.
=aria_role= is =dialog=, the title doubles as the =aria_label=; wired
through =kind=/=view_to_json=/=serialize_view= + both renderers (=▌ modal:=
in tui, =<div role="dialog" class="modal">= in web); =ALL_NODE_KINDS=
9→10, =modal_node= constructor. Hermetic proof in =rich_view.rs=: title
above body, dialog role + label, JSON nests the body. =just check= 3507.
*** Decision (2026-06-28) Modal is a node, not a shell-side =bool=.
A modal could be a flag the shell special-cases, but making it a =Node=
keeps overlays inside the one declarative tree every renderer already
walks — so the palette/confirm/prompt all render through the SAME path
(and the V1c exhaustive-match parity guard covers them for free). The
body is a =Box<Node>= so any view (rows, palette, detail) can be the
overlay content. Dim/animation are the embedder's pixels, not gated.
*** DONE G1c =Node::Toast= — transient severity-classed notification
=Node::Toast { level: ToastLevel, text }= is the notification a shell
flashes for an async outcome. =ToastLevel= (Info/Success/Warning/Error)
drives both the CSS class (=toast-error=) and the a11y live-region role
(=alert= for warn/error, =status= for info/success). Wired through
=kind=/=aria_role=/=view_to_json=/=serialize_view= + both renderers (=⚑
[level]= tui, =<div role=… class="toast toast-…">= web); =ALL_NODE_KINDS=
10→11, =toast_node= constructor. =view_to_json= crossed clippy's 100-line
bar (11 exhaustive arms) → =#[allow(too_many_lines)]= with rationale, the
established precedent for flat one-arm-per-kind matches. =just check= 3514.
*** Decision (2026-06-28) Scope G1c to Toast; badges/icons/focus → G5.
The G1 header is "splits / overlays / notifications"; Toast completes that
trio. Row badges, icons-as-data, and a focus marker are *presentational
attributes on existing nodes* (a wide =RowView= field change across 11
construction sites) and belong with hover/active/disabled — so they move
to G5 (interaction states), where the whole interaction-attribute surface
lands in one coherent cycle rather than churning =RowView= twice. Honest
re-scope, recorded; no capability dropped, just regrouped.

** DONE G2 Declarative typed theme tokens [1/1]
=closure_shell_core::Theme= = a =Palette= (8 =ColorRole= slots) + =Spacing=
+ =Typography= as data, with three =const= built-ins (dark / light /
high-contrast). =Theme::from_name= resolves the free-form =config.theme=
string (case-insensitive: =light=, =high-contrast=/=hc=, else =dark=) — no
runtime stylesheet parsing, the whole theme is typed values. =Color= is an
=#rrggbb= newtype whose =rgb()= parses to bytes and resolves malformed
input to black (never a panic, I5). Each shell maps the tokens natively:
=closure_shell_web::theme_css_variables= emits the =:root= CSS custom
properties, =closure_tui::theme_color= turns a =ColorRole= into a ratatui
=Color::Rgb=. 10 tests (resolve/contrast/hex-parse/roles/css/rgb across
shell-core+web+tui), all hermetic. =just check= 3524 green.
*** Decision (2026-06-28) Tokens as typed data, not a CSS/theme file.
A "themeable" app usually ships a stylesheet the user edits; that puts an
untyped parser on the hot path and makes a bad colour a runtime failure.
Instead the palette is a typed Rust value (=ColorRole= → =Color=), so the
three built-ins are =const=, resolution is total, and a malformed hex is
black not a crash. The free-form =config.theme= string already existed
(coarse =ThemeKind= for egui); =Theme::from_name= is the richer 3-way
resolver over the SAME string, leaving the egui =ThemeKind= path
untouched (no churn to a feature-gated shell). Shells own only the
token→native mapping (CSS var / ratatui Color), so a 4th theme or a 9th
role is one data edit + the exhaustive =color= match, not per-shell work.

** DONE G3 GTK4 editor parity [1/1]
GTK4 was a read-only headline list (=rows()=); G3 lifts it to editor
parity with tui/egui/gpui. =closure-shell-gtk= now depends on
=closure-shell-core=, re-exports the shared =App=/=Shell=, and renders the
full =ViewTree= via =widget_tree(&Node) -> String= — a deterministic GTK4
widget-tree descriptor (=GtkFrame=/=GtkBox=/=GtkListBox=/=GtkEntry=/
=GtkDialog=/=GtkInfoBar=…), exhaustive over every =Node= kind so it tracks
the G1 vocabulary at compile time (V1c). Editing goes through the shared
=Shell= (I8): =tests/widget_tree.rs= proves a =Shell::capture= shows up in
the rebuilt tree AND persists to disk. =run()= builds the same structure
with real =gtk4= widgets (display-bound, =gtk= feature). Default =just
check= 3527 green (feature OFF, hermetic); =--features gtk= build-verified
under =nix develop .#webview=.
*** Decision (2026-06-28) gtk renders the ViewTree, not a private model.
The old gtk shell had its own =rows()= list — a second, untested UI model.
G3 makes gtk a real =ViewTree= renderer (a third =render_view=, beside
tui text + web HTML) over the SAME =App=/=Shell= every other shell drives,
so editor behaviour is the tested shared core and the only gtk-specific
code is the =Node=→widget mapping. That mapping is a hermetic string
(=widget_tree=, like qt's =qml_document=) so the structure is golden-tested
without a display; the real =gtk4= build is the thin window. =rows()= is
kept for the legacy path but is no longer the shell's ceiling.

** DONE G4 Qt6/QML editor parity [1/1]
The Qt shell mirrors G3: =closure-shell-qt= now depends on
=closure-shell-core=, re-exports the shared =App=/=Shell=, and renders the
full =ViewTree= via =qml_view(&Node) -> String= — a =QtQuick.Controls=/
=Layouts= document (=GroupBox=/=ColumnLayout=/=RowLayout=/=TextField=/
=Dialog=/=Label=…) exhaustive over every =Node= kind (V1c), with QML
string-literal escaping. Editing goes through the shared =Shell= (I8):
=tests/qml_view.rs= proves a =Shell::capture= appears in the QML and
persists to disk, plus quote-escaping + the rich-kind coverage. =run()=
loads =qml_view(App::view(Shell))= in a real =qmetaobject= engine
(display-bound, =qt= feature). =qml_item='s flat 11-arm match took the
=#[allow(too_many_lines)]= precedent. Legacy =qml_document= kept. Default
=just check= 3530 green; =--features qt= build-verified under =.#webview=.
*** Decision (2026-06-28) qml_view supersedes qml_document as the ceiling.
=qml_document= rendered only a flat =ListView= of headline strings — the
read-only past. =qml_view= renders the SAME =ViewTree= every other shell
draws, so Qt editor behaviour is the tested shared =App=/=Shell= and the
only Qt-specific code is the =Node=→QML mapping (a hermetic string, like
gtk's =widget_tree=). Two shells (gtk + qt) now prove the pattern
generalises: any embedder is "render the =ViewTree= + drive the =Shell=",
the bulk hermetic, the window a thin display-bound adapter.

** DONE G5 Interaction states + Notion affordances [3/3]
Row presentation + interaction surfaces, hermetic state. Sub-cycles: G5a
badges/icons-as-data (moved from G1c), G5b interaction states
(hover/focus/active/disabled), G5c Notion affordances (slash-menu, block
"+", drag-reorder as commands).
*** DONE G5a Row badges + icons-as-data
=RowView= grew an =icon: Option<String>= (a TODO-status glyph: ● done / ○
open / ◆ other) and =badges: Vec<String>= (tags, priority chips), with a
=new()= constructor + =with_icon=/=with_badges= builders that default both
empty (back-compat for all 11 construction sites). =browse_view= populates
them from the headline (=todo_glyph(todo)= + =h.tags()=); every renderer —
=view_to_json=, =serialize_view=, tui, web, gtk =widget_tree=, qt
=qml_view= — draws them, empty-safe so existing goldens are untouched.
Tests: row icon/badges as JSON data + =browse_view= maps =:tags:= → badges
and TODO → an icon. =just check= 3532 green.
*** Decision (2026-06-28) Presentation lives on RowView, populated centrally.
Badges/icons are data on the row, not per-shell decoration, so all six
renderers show the same chips from one source (and a shell can style them
natively). They default empty via the builder, which is why adding two
fields to a struct with 11 construction sites stayed a mechanical,
golden-safe change. The =App::view= browse path sets the icon (its =Row=
has the TODO) but not badges (=Row= has no tags yet); =browse_view= is the
full path. Enriching =Row= with tags is a later cycle, recorded not faked.
*** DONE G5b Interaction states (hover/focus/active/disabled)
=Interactions= is a hermetic state machine over element indices: =focus=/
=blur=/=focus_next=/=focus_prev= (wrapping), =hover(Some|None)=, =press=/
=release=, =set_disabled=. =state_of(i)= resolves a single =ElementState=
under a fixed precedence =Disabled > Active > Focused > Hovered > Normal=
(disabled is absorbing). Pure + deterministic — a shell paints the focus
ring / hover / pressed / dimming from this one source, the pixels being
the embedder's. 7 tests (each transition + precedence + wrap). =just
check= 3539 green.
*** Decision (2026-06-28) Interaction is shared state, not per-shell glue.
Hover/focus/active/disabled usually live as ad-hoc booleans inside each
GUI's event handler — untestable and divergent. Modelling them as a
=Interactions= machine with one precedence rule means the *behaviour* (a
disabled element ignores focus visually; press beats focus) is tested once
and identical everywhere; each shell only maps =ElementState= → its native
style. Indices (not node refs) keep it dep-free and =Copy=-cheap. The
focus marker G1c deferred lands here as =Interactions::focused=.
*** DONE G5c Notion affordances (slash-menu, block "+", drag-reorder)
Three Notion affordances, each reduced to a kernel command / pure state:
=slash_menu(query, mode)= is the "/" command menu (fuzzy-filtered
=PaletteItemView=s carrying their chords, reusing =PALETTE_COMMANDS= +
=fuzzy_score=); =block_insert_action(mode)= is the block "+" (the
=add-sibling= command + chord, V1); =DragReorder= (=begin=/=over=/=drop=/
=cancel=) + =reorder_indices(len, from, to)= model drag-to-reorder as a
pure gesture + index computation (out-of-range = identity, I5), the drop
mapping to a registry move (I8). 6 tests. =just check= 3545 green.
*** Decision (2026-06-28) Affordances reduce to commands, not new verbs.
Notion's slash menu / "+" / drag are *surfaces*, not new capabilities —
each already had a command (=add-sibling=, =move=, the palette). G5c models
the surface (a filtered menu, an action handle, a from/to gesture) and
routes it to the existing registry command (I8), so no affordance is a
shell-private mutation path. =DragReorder= holds indices + yields =(from,
to)=; computing the new order (=reorder_indices=) is pure and the move is
the kernel's — the gesture can't desync from the data.

** DONE G6 Palette + which-key polish [1/1]
=command_palette(query, mode)= upgrades the flat palette into a sectioned,
fuzzy-ranked menu: =PALETTE_COMMANDS= now carries =(label, canonical,
section, description)=, and the palette groups commands by =PALETTE_SECTIONS=
(Navigate / Edit / Mode / App), fuzzy-ranks within each section, drops
empty sections, and gives every =PaletteEntry= a human description + its
chord (V1). =serialize_palette= is the deterministic snapshot (I6) a shell
renders verbatim — one source, so the palette/which-key is identical across
GUIs. The three existing palette consumers (slash_menu, palette_results,
=App::view=) updated to the 4-tuple. 3 tests. =just check= 3548 green.
*** Decision (2026-06-28) Description + section are data on the command row.
The palette was =(label, chord)= pairs — no grouping, no help text. Rather
than per-shell section logic, the section + description live on
=PALETTE_COMMANDS= itself, so =command_palette= is a pure transform and
every GUI renders the same grouped, described, ranked menu from one place.
Sections render in a fixed order with empties dropped, so the layout is
deterministic and a query narrows visibly. =serialize_palette= keeps the
rendering golden-testable; the chord still comes from =chord_for_command=
(I4), never hardcoded.

** DONE G7 Async feedback surface [1/1]
=Feedback= is a typed queue for async outcomes: =notify(level, text)=
appends a severity message, =progress(label, percent)= updates a labelled
progress entry *in place* (a running sync/eval/llm op reports incrementally,
not stacking), =clear()= settles a batch. =FeedbackKind= is
Info/Success/Warning/Error/Progress(u8). =to_nodes()= renders every item as
a =Node::Toast= (G1c) — progress as a polite =Info= toast with =label N%= —
so every shell already displays notifications + progress with zero
per-shell notification code. 4 tests. =just check= 3552 green.
*** Decision (2026-06-28) Feedback renders through the Toast vocabulary.
G1c added =Node::Toast=; G7 is the *state* that produces toasts. Making
=Feedback::to_nodes()= emit =Node::Toast= means the async surface inherits
every renderer (tui/web/gtk/qt) for free — the reason G1c shipped the
vocabulary before G7 filled it. Progress is modelled as a percent on a
labelled entry updated in place, so a long op is one moving toast, not a
flood; collapsing it to an =Info= toast keeps the a11y politeness right
(=status=, not =alert=). The op itself still runs wherever it runs; this is
only the report.

** DONE D2 Content hash: FNV-1a → cryptographic BLAKE3 [1/1]
=closure_sync::Cid::of= was a non-cryptographic FNV-1a digest (prefixed
=b1=) — fine for dedup, useless as an integrity guarantee. Now a 256-bit
BLAKE3 digest (prefixed =b3=, pure-Rust =blake3=, hermetic). Pinned in
=cas.rs::cid_is_blake3_256bit= two ways: against the lib's own digest
(algorithm is exactly BLAKE3) and against the published empty-input test
vector (it is *canonical* BLAKE3). =BlockStore::verify= now rests on real
collision resistance: a tampered blob provably cannot reuse its =Cid=.
After this the user can trust content-addressed dedup + verify-on-read as
a security property, not just a checksum.
*** Decision (2026-06-26) BLAKE3 over SHA-256/blake2.
BLAKE3 is pure-Rust, builds offline (I10 holds — confirmed: =just check=
needs no network for it), fast, and 256-bit collision-resistant. =snow=
already pulls blake2 but not as a general hash API; a dedicated =blake3=
dep is cleaner than reusing the Noise primitive. =Cid= value stays an
opaque string so a later swap needs no API change. Old =b1= ids simply
never match new =b3= ids — acceptable, content re-hashes on read.

The vision's headline feature ("compose existing building blocks into
new blocks/widgets"). Options: (a) a bespoke widget/block-type model
and composition DSL; (b) use org's native composition. Taken (b):
one headline = one addressable block (stable :ID:, I2); blocks nest
via the outline tree; "new composed blocks" are named org structures —
=#+BEGIN: closure-view= is a composed database block, =#+BEGIN_SRC=
is a compute block (Coda-style formulas), and bodies hold code/tables/
text. This keeps everything plain-text/org-compatible (no JSON widget
schema), git-diffable, and editable in every shell. Reversible: a
typed-block/widget layer can sit on top of the Document IR later
without changing the file format. A bespoke widget DSL is out of scope.
** Editing modes across shells: TUI is modal, GUIs are launcher-style (2026-06-14)
The vision wants notion/emacs/vim/doom/helix "consistently in every UI
element." =closure-input::mode_keymap= is now the single source of
truth for all five modes (TUI consumes it directly). But the GUI
shells (gpui, egui) are type-to-filter launchers (the vision's
"Notion-like default ... should probably be the default", vertico
feel), and a launcher fundamentally conflicts with bare-letter modal
command surfaces — you can't type "ship" to filter if "s" is a
command. Options: (a) force a modal command-surface Browse on the
GUIs (kills the launcher feel, and I can't visually verify a GUI
interaction rewrite headless); (b) keep GUIs as launchers and realize
full modes only in the keyboard-centric TUI. Taken (b): the TUI is the
modal shell; the GUIs consume the shared keymap for the mode label,
which-key hints, and a cycle affordance (C-t in gpui), while keeping
type-to-filter in every mode. Reversible: a future "modal GUI" can add
a command-surface Browse consuming the full keymap once it can be
tried on screen.
** GUI shells: egui + web shipped, gpui opt-in, Tauri/Flutter/GTK4/Qt6 dropped (2026-06-13)
The vision lists CLI, TUI, gpui, single-HTML, web, Tauri, Flutter,
GTK4, Qt6 as *suggestions, not must-haves*, and explicitly invites
dropping or substituting them. The hermetic, dep-minimal kernel (I10)
can't absorb the toolchains those native shells need (node + tauri-cli,
the Flutter SDK, GTK, Qt) without breaking reproducible nix builds.
Resolution: ship egui (default native, kernel-side =Shell= + tests)
and the web shell / self-contained HTML export (cross-platform, zero
native deps); ship gpui as an opt-in =gpui=-feature crate (real window
over a headless-tested state core; built+linked behind the feature —
see below).
Tauri/Flutter/GTK4/Qt6 are DROP as workspace crates: the two empty
stub crates were removed, but the CLI capability matrix keeps them as
comparison rows so the "type-level venn" of shells stays complete.
Reversible: any of them can return as an *external* packaging project
that consumes the kernel (the web shell is the obvious substrate for a
webview wrapper) without touching the hermetic workspace.

** Perf guards use std::time::Instant, not criterion (2026-06-13)
The input-lag budget and rescan-avoided "benchmarks" are plain
=#[test]= functions timing the hot path with generous thresholds
(16ms nav, 50ms fuzzy) and asserting the incremental-reload reparse
count is 0. Avoids adding criterion (a heavyweight dev-dep) to a

** Tree-sitter highlighting: KeywordHighlighter as dep-free default (2026-06-13)
Extensive research (code, org CodeBlockView + content spans, TUI FileView
source rendering, fixtures with #+BEGIN_SRC, tree-sitter-highlight + CLI
ecosystem in 2026) confirmed that embedding full tree-sitter (with language
crates and queries) pulls unsafe + non-trivial build/packaging cost,
conflicting with I5 (no panics/unsafe in kernel), I10 (hermetic), and
existing project comments. 
Approach taken: implement KeywordHighlighter (pure-Rust, zero deps) as the
always-available concrete impl of the Highlighter trait. It satisfies the
strict gap-free full-coverage contract and the pre-written tests for
common org-babel languages. The trait remains the stable pluggable surface
for shells. Real tree-sitter support can be added later via optional
feature (tree-sitter-highlight) or external CLI wrapper (invoked when
available) without changing the API or bloating the default build.
TUI integration of highlights in file view is the immediate next small
TDD cycle. Reversible: swap the default impl or add cfg(feature = "tree-sitter")
later. Decision recorded after research + TDD cycle that wrote tests first,
ran to failure, implemented, verified (tests + clippy -D warnings + checks).
** Cron daemon = system cron / shell loop, not an in-process timer (2026-06-13)
=closure cron= runs one tick of due jobs (clock injectable via
=--at=). Rather than embedding a timer thread in the CLI, the daemon
is the OS scheduler: a crontab entry =* * * * * closure cron <vault>
<file>= or a =while sleep 60= loop. Keeps the kernel free of timer
plumbing and is literally cron-compatible (the vision's word).
Reversible: an in-process =--daemon= loop can wrap the same tick
later. closure-cron's Scheduler already exists for embedders who
want it.
** Command replay from history deferred (2026-06-13)

command) needs structured, machine-replayable journal entries rather
than the current human-readable text headlines. Deferred until a

=:CMD:= property to journal entries later without breaking the text
form. The queryable-history capability is delivered now.

The roadmap asked for file:line. The parser is span-preserving but

** org2 decision: track upstream org-mode as compatibility target; org2 export-only (2026-06-13)
Context: org-mode (Emacs) is the de-facto plain-text PKM format with
decades of files, tooling, and users. The parser scope (spec.md) and
all golden roundtrips (I1) target a practical subset of current upstream
org (headlines+TODO+tags+drawers+babel blocks+lists+timestamps+links+...).
Options considered: (a) track Emacs org git master as "the" target and
only add constructs when they land upstream + we can roundtrip them
byte-exact; (b) invent "org2" as a forward-compatible evolution inside
this project and make the parser accept both; (c) treat org2 as a
separate future format.
Reversible default taken (a): treat current Emacs org-mode as the
compatibility target for closure-org. Any "org2" (major syntax rev or
new upstream experiment) is export-only (via closure-markdown style
crate or dedicated exporter) — never the on-disk default or primary
parse target. Rationale: chasing an in-flight org2 would violate I1
(byte-exact on committed corpus), I5 (hand-written recursive descent
+ fuzz + #![forbid(unsafe)] stays tractable only for a bounded subset),
I10 (hermetic reproducible nix builds; external grammar crates or
complex conditionals hurt), and the "built to last" primitives (parse
stays simple + span-preserving). Existing org files and workflows keep
working; richer export paths can be added without perturbing the kernel
or forcing users to migrate. Reversible: later add an org2 feature
crate or export mode (behind cfg or CLI flag) that consumes the same
Document IR and emits the new syntax; the core parser contract and
vault stay on upstream-org-compat. Recorded after full project review
of parser, fixtures, invariants, and prior md-compat decision.
