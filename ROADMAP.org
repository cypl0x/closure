#+title: closure — capability roadmap
#+todo: TODO(t) WIP(w) | DONE(d) DROP(x)

Working agreement for autonomous sessions: work top-down, pick the
highest =TODO=, split it into small TDD cycles, flip it to =DONE= in the
same commit that finishes it. Every item must pass the test "after this
the user can ___, which they could not before" — if the blank only
names a new method, the item does not belong here. Statistics/alias
accessor methods on closure-org/store/input are done; add no more
unless a feature in the same cycle calls one. Architecture contract
lives in [[file:docs/spec.md][spec.md]] (invariants I1–I10) and [[file:docs/phases.md][phases.md]] (milestones); this
file is the fine-grained, capability-level queue between them. Blocked
on a design decision? Record it under [[*Decisions][Decisions]], pick the most
reversible option, keep moving.

** Network sniffer real backend is DROP (out-of-tree plugin) (2026-06-14)
The vision wants an included sniffer (Little Snitch/wireshark/mitmproxy
class). A real capture backend needs libpcap or shelling to
tcpdump/ss with root/CAP_NET_RAW — non-hermetic, privileged, and
platform-specific, which conflicts with I10 and the dep-minimal core.
Taken: the hermetic crate ships the pluggable =CaptureBackend= trait,
a =MockBackend=, the blocklist config + =closure sniff= decision view,
and the org-native capture log. A real backend is an external plugin
implementing the trait (loaded via closure-plugin-host). Reversible:
add an optional =pcap= feature crate behind a flag later. The
composable/blockable/mockable/config goals are met; live capture is
the plugin's job.
** Composable blocks = org-native nesting + named dynamic blocks (2026-06-14)
The vision's headline feature ("compose existing building blocks into
new blocks/widgets"). Options: (a) a bespoke widget/block-type model
and composition DSL; (b) use org's native composition. Taken (b):
one headline = one addressable block (stable :ID:, I2); blocks nest
via the outline tree; "new composed blocks" are named org structures —
=#+BEGIN: closure-view= is a composed database block, =#+BEGIN_SRC=
is a compute block (Coda-style formulas), and bodies hold code/tables/
text. This keeps everything plain-text/org-compatible (no JSON widget
schema), git-diffable, and editable in every shell. Reversible: a
typed-block/widget layer can sit on top of the Document IR later
without changing the file format. A bespoke widget DSL is out of scope.
** Editing modes across shells: TUI is modal, GUIs are launcher-style (2026-06-14)
The vision wants notion/emacs/vim/doom/helix "consistently in every UI
element." =closure-input::mode_keymap= is now the single source of
truth for all five modes (TUI consumes it directly). But the GUI
shells (gpui, egui) are type-to-filter launchers (the vision's
"Notion-like default ... should probably be the default", vertico
feel), and a launcher fundamentally conflicts with bare-letter modal
command surfaces — you can't type "ship" to filter if "s" is a
command. Options: (a) force a modal command-surface Browse on the
GUIs (kills the launcher feel, and I can't visually verify a GUI
interaction rewrite headless); (b) keep GUIs as launchers and realize
full modes only in the keyboard-centric TUI. Taken (b): the TUI is the
modal shell; the GUIs consume the shared keymap for the mode label,
which-key hints, and a cycle affordance (C-t in gpui), while keeping
type-to-filter in every mode. Reversible: a future "modal GUI" can add
a command-surface Browse consuming the full keymap once it can be
tried on screen.
** GUI shells: egui + web shipped, gpui opt-in, Tauri/Flutter/GTK4/Qt6 dropped (2026-06-13)

GTK4, Qt6 as *suggestions, not must-haves*, and explicitly invites
dropping or substituting them. The hermetic, dep-minimal kernel (I10)
can't absorb the toolchains those native shells need (node + tauri-cli,
the Flutter SDK, GTK, Qt) without breaking reproducible nix builds.
Resolution: ship egui (default native, kernel-side =Shell= + tests)
and the web shell / self-contained HTML export (cross-platform, zero
native deps); ship gpui as an opt-in =gpui=-feature crate (real window
over a headless-tested state core; built+linked behind the feature —
see below).
Tauri/Flutter/GTK4/Qt6 are DROP as workspace crates: the two empty
stub crates were removed, but the CLI capability matrix keeps them as
comparison rows so the "type-level venn" of shells stays complete.
Reversible: any of them can return as an *external* packaging project
that consumes the kernel (the web shell is the obvious substrate for a
webview wrapper) without touching the hermetic workspace.

** Tree-sitter highlighting: KeywordHighlighter as dep-free default (2026-06-13)

feature (tree-sitter-highlight) or external CLI wrapper (invoked when
available) without changing the API or bloating the default build.

TDD cycle. Reversible: swap the default impl or add cfg(feature = "tree-sitter")
later. Decision recorded after research + TDD cycle that wrote tests first,
ran to failure, implemented, verified (tests + clippy -D warnings + checks).
** Cron daemon = system cron / shell loop, not an in-process timer (2026-06-13)
=closure cron= runs one tick of due jobs (clock injectable via
=--at=). Rather than embedding a timer thread in the CLI, the daemon
is the OS scheduler: a crontab entry =* * * * * closure cron <vault>
<file>= or a =while sleep 60= loop. Keeps the kernel free of timer
plumbing and is literally cron-compatible (the vision's word).
Reversible: an in-process =--daemon= loop can wrap the same tick
later. closure-cron's Scheduler already exists for embedders who
want it.

=:CMD:= property to journal entries later without breaking the text

** Dead-link locations use block ids, not line numbers (2026-06-12)
The roadmap asked for file:line. The parser is span-preserving but

** org2 decision: track upstream org-mode as compatibility target; org2 export-only (2026-06-13)
Context: org-mode (Emacs) is the de-facto plain-text PKM format with
decades of files, tooling, and users. The parser scope (spec.md) and
all golden roundtrips (I1) target a practical subset of current upstream
org (headlines+TODO+tags+drawers+babel blocks+lists+timestamps+links+...).
Options considered: (a) track Emacs org git master as "the" target and
only add constructs when they land upstream + we can roundtrip them
byte-exact; (b) invent "org2" as a forward-compatible evolution inside
this project and make the parser accept both; (c) treat org2 as a
separate future format.
Reversible default taken (a): treat current Emacs org-mode as the
compatibility target for closure-org. Any "org2" (major syntax rev or
new upstream experiment) is export-only (via closure-markdown style
crate or dedicated exporter) — never the on-disk default or primary
parse target. Rationale: chasing an in-flight org2 would violate I1
(byte-exact on committed corpus), I5 (hand-written recursive descent
+ fuzz + #![forbid(unsafe)] stays tractable only for a bounded subset),
I10 (hermetic reproducible nix builds; external grammar crates or
complex conditionals hurt), and the "built to last" primitives (parse
stays simple + span-preserving). Existing org files and workflows keep
working; richer export paths can be added without perturbing the kernel
or forcing users to migrate. Reversible: later add an org2 feature
crate or export mode (behind cfg or CLI flag) that consumes the same
Document IR and emits the new syntax; the core parser contract and
vault stay on upstream-org-compat. Recorded after full project review
of parser, fixtures, invariants, and prior md-compat decision.
