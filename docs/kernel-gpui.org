#+TITLE: closure — kernel + gpui work queue
#+STARTUP: overview

Scope is the kernel (closure-org, closure-core, closure-store,
closure-query, closure-config, closure-input, closure-undo,
closure-eval, closure-whichkey, closure-shell-core), the gpui shell,
and closure-cli only where the window needs it. Every other crate is
frozen: it keeps compiling and stays green, and gains no features.

Rules for this file:

- One =* TODO= per deliverable, small enough to finish in one commit.
- Every item carries an =Acceptance:= line that is a runnable command.
- Items may be ADDED at any time. Every bug found and every "we
  should" gets written down here before it is acted on.
- An item is never deleted, reworded, or merged to shrink the queue.
  The count drops only by finishing work.
- TODO -> DONE only after the commit lands, with the answer in the
  item's body.

* DONE Spec: define what a block is
The first item in the vision is composability and it is the least
built. Nothing under "Composition" below can be tested until this
says what composes with what.

Decide and write into =docs/spec.md=: is the unit a headline, an
element, or both? What may appear inside a composed block? What is
its identity under I2? What does composition mean for I1 roundtrip —
does an expansion ever reach the file, or only the view?

Acceptance: =grep -c "^### I12" docs/spec.md= prints 1, and
=nix develop -c cargo test -p closure-shell-core --test what_a_block_is= passes.

Three tiers: an *addressable block* is a headline and is the only
thing with an identity (I2); a *content block* is an org element and
is what a template is made of; a *composable block* is a named widget
with declared inputs. A widget never contains a headline — a template
that emitted one would either mint the same id at every call site or a
new one on every render, breaking I2 or I6.

The load-bearing half is I12: an expansion is never written back.
Org's dynamic blocks work the other way round and closure cannot,
because then a file's bytes would depend on when it was last
refreshed. That keeps composition inside `query`, one of the seven
kernel primitives, so it adds no eighth.

(The acceptance line named a `spec_is_true` test that does not exist;
the check it meant is the one above, which does.)

* DONE Spec: I11 performance budgets, with numbers
"Almost no input lag" cannot be tested. State p99 keystroke->frame,
cold vault open, and a memory ceiling, each at a stated headline
count, and say which are machine-pinned and which are portable
shapes.

Acceptance: =grep -c "^### I11" docs/spec.md= prints 1.

Stated per *headline*, not per vault — which is what makes them
portable and therefore worth failing a build over. 100 us/headline to
open, 8 KB/headline resident, 1000 us to derive one keystroke;
measured at 2.9 us, 2 KB and 3 us. Order-of-magnitude guards: they
fail on an accidental quadratic, not on a slow laptop, and the shape
tests remain the sensitive ones.

No frame budget, deliberately: this machine has no Vulkan driver, so a
frame time measured here would describe lavapipe rather than closure.
The question the kernel owns is what a keystroke makes it derive.

* DONE Spec: state the target scale
The store parses the whole vault into memory. That is a load-bearing
decision made by accident. Say the number the kernel promises to
hold.

Acceptance: =grep -ci "target scale" docs/spec.md= is at least 1.

100,000 headlines — about 15 MB of org. Measured on this machine,
release: 10k headlines open in 32 ms for 27 MB resident, 100k in
285 ms for 196 MB, both linear at ~2.9 us and ~2 KB each. A million
would be ~3 s and ~2 GB, which is where parsing the whole vault stops
being the right design, so the promise stops below it on purpose.
=closure_store::TARGET_SCALE_HEADLINES= carries the same number and
=closure-store/tests/target_scale.rs= fails if the two disagree.

* DONE Widget: named parameters at the call site
=({{name}})= substitution is =#define=, not composition. A call site
must be able to pass values.

Acceptance: =nix develop -c cargo test -p closure-query --test widget_params=

A widget declares what it takes (=:inputs who,title=) and a reference
carries arguments (={{card title=Today note="write the parser"}}=).
Inside the body a parameter is read with the same ={{who}}= a widget
reference uses, and an argument shadows a widget of the same name —
locals beat globals, so a widget can be written without knowing every
name in the vault.

The declaration is not ceremony: a widget block is its own call site
with no arguments, so ={{who}}= in an undeclared widget cannot be told
apart from a reference to a widget nobody defined, and that has to
stay an error. Declared and unbound expands to nothing; undeclared is
still a widget lookup, so a typo is still an error.

Verified in the window only as far as the window allows — it shows the
template verbatim and never an expansion, which is I12 doing its job
for the editor and a missing read view everywhere else. Written down
as its own item.

* DONE Widget: typed inputs validated at load
I9 says config errors fail the load. A widget's declared inputs are
config. A missing or wrong-typed argument is an error before render,
not a hole in the output.

Acceptance: =nix develop -c cargo test -p closure-query --test widget_types=

=:inputs count:number,title,done:bool=. Three types, because a type
system here earns its place catching the mistakes that are always
mistakes and stops earning it the moment a template needs a grammar to
describe its own arguments. Untyped stays text, which is what every
input written before today is.

Two errors, both carrying everything needed to fix them without
opening another file: =UnknownArgument= for a call site naming an
input that does not exist (the typo that used to render as silence),
and =BadArgument= for a value the type cannot hold. Missing is
deliberately not an error — a definition block is a call site with no
arguments, and showing a template is not a mistake.

Not visible in the window yet: nothing paints widget errors, or
widgets. Both are items of their own.

* DONE Widget: slots
Content passed *into* a widget body, so a widget can wrap what it is
given rather than only emit what it knows.

Acceptance: =nix develop -c cargo test -p closure-query --test widget_slots=

={{...}}= has nowhere to put a block, so the call site that carries
content is a block itself: =#+BEGIN: closure-widget :call panel :with
title=Notes=, body is the content, ={{slot}}= inside the widget is
where it lands. =:name= defines, =:call= invokes — one keyword apart,
and both are ordinary org dynamic blocks, so a file full of them still
opens in Emacs.

=slot= is always in scope, empty when there is none, so ={{slot}}= in
a widget nobody passed content to is not mistaken for a widget nobody
defined. The content is expanded in the caller's scope before the
callee sees it, the same rule as an argument's value.

Verified on :1: a panel wrapping two list items.

* DONE Widget: cycle detection with a depth limit and a named path
An expansion cycle must fail with the chain that caused it, not a
stack overflow and not a silent stop.

Acceptance: =nix develop -c cargo test -p closure-query --test widget_cycles=

The error carries the whole ring, from where it closes rather than
from where expansion began — the widgets before it are on the way in,
not part of it. On :1: =widget cycle: page -> panel -> header -> page=
in the pane where the widget is.

Depth is a separate failure and now has its own error. A chain nesting
5,000 deep without ever repeating a name is not a cycle, and recursing
it would end the process — which I5 forbids more strongly than it
forbids a panic, because a blown stack takes the window with it. The
limit is 64: far past what a page needs, far below what this expander
can survive.

* DONE LSP: composition errors as diagnostics with precise ranges
Acceptance: =nix develop -c cargo test -p closure-lsp --test diagnostics=

They were already diagnostics; they were all reported at the first
=#+begin: closure-widget= line in the file, whatever had gone wrong

* DONE Org conformance: harness and pass-rate command
A corpus of real org files and a command that reports what fraction

Acceptance: =nix develop -c ./target/debug/closure conformance= prints a percentage.

* DONE Org: timestamp repeaters
=+1w=, =.+1d=, =++1m= on SCHEDULED/DEADLINE. A task tool without
repeaters is not a task tool.

Acceptance: =nix develop -c cargo test -p closure-org --test repeaters=

All three kinds, all five units, parsed and advanced. They differ only
in what "next" means when you are late, which is the whole reason org
has three: =+1w= lands on the next date in the original series, =++1w=
skips what was missed, =.+1w= counts from today. A warning period
(=-2d=) is not a repeater and is not read as one.

Conformance 61% -> 67%.

Civil-date arithmetic moved from closure-shell-core down to
closure-org on the way: it is arithmetic on org timestamps, and the
layer that parses them is where it belongs. shell-core re-exports the
names it was written against.

* DONE Kernel: marking a repeating task DONE advances its date
Parsing a repeater is not the feature; the feature is that finishing
the weekly review schedules the next one instead of closing it. That
is a command, and I3 says every mutation is undoable, so it belongs in
closure-core rather than in a shell.

Acceptance: =nix develop -c cargo test -p closure-core --test repeat_on_done=

Three changes that undo as one: the keyword goes back to TODO, the
date moves on, and =:LAST_REPEAT:= records when this occurrence was
finished. One undo getting the keyword back but keeping next week's
date would leave a document that never existed, so it is a single
=Edit::Repeat= rather than three edits.

Needed =rewrite_headline_remove_property=, which did not exist: undo
has to leave the drawer as it found it, and setting a property to an
empty string leaves =:LAST_REPEAT: = behind. Removing the last entry
takes the drawer with it, for the same reason.

End to end: =closure set-todo tasks.org <id> DONE= on a =+1w= task
moved 2026-08-11 to 2026-08-18 and left it TODO.

* DONE Org: #+INCLUDE resolution
Acceptance: =nix develop -c cargo test -p closure-org --test include=

Composition by file, and it gets the composition rules already

* DONE Org: entities and LaTeX fragments
Acceptance: =nix develop -c cargo test -p closure-org --test entities=

Two constructs in one commit because they are the same question asked
twice: which run of characters in this line is maths or a named
character rather than prose. =fragments()= answers it; =entity_char()=
gives the glyph for the names closure knows, and =None= rather than a
guess for the rest.

The interesting rule is the dollar. A digit just after an opening =$=
is money, which is what separates "$5" from "$x^2$" — and a digit just
before the closing one is ordinary, because =$x^2$= ends in a 2. The
first version applied the digit rule to both ends and rejected all
maths; the test for =$x^2$= caught it immediately.

Conformance 67% -> 73%.

* DONE Org: inline tasks
Acceptance: =nix develop -c cargo test -p closure-org --test inline_tasks=

Fifteen stars is org's inline task: a task attached to the paragraph
it sits in rather than a section of the document. closure read it as
an ordinary level-fifteen headline, so a note with one in it had a

The parser stops at fifteen and =inline_tasks()= finds them instead —

* DONE Org: column view (#+COLUMNS)
Acceptance: =nix develop -c cargo test -p closure-org --test column_view=

=%25ITEM(Task) %TODO %EFFORT{+}= — width, property, title, summary.
A file saying how it wants to be tabulated is the same idea a
=closure-view= block expresses from the other end; this is the part
that lets the *file* ask.

Braces are read before parentheses: a summary can follow a title, and

unrecognised summary is kept as no summary rather than refused — org
has a dozen and closure knows four, and a format nobody implemented
should not make a document unreadable, the same rule an unknown widget

* DONE Org: #+TBLFM table formulas
Acceptance: =nix develop -c cargo test -p closure-org --test tblfm=

Reads and evaluates; writing the answers back into the file is a
mutation and so is a command, undoable, and its own item below — the
same split composition landed on, for the same reason.

The subset is column assignments over the four operators, numeric
literals and =$N= references, left to right without precedence, which
is what the formulas people actually write look like. Org's ranges,
=vsum=, =@row= addressing and lisp are not here and the matrix says
so by what it does not claim.

A row whose referenced cells are not numbers keeps the target cell it
already had, and so does a division by zero: blanking it would lose
what the author typed, and a formula is not a licence to do that.

Conformance 82% -> 85%.

* DONE Kernel: recomputing a table's formulas is a command
=eval_table_formulas= says what the cells should be; nothing puts them
back. In org that is =C-c C-c= on the formula line, and here it is a
mutation — so it belongs in closure-core behind the registry, with an
Edit the undo tree can reverse (I3/I8).

Acceptance: =nix develop -c cargo test -p closure-core --test recompute_table=

One edit for the whole table rather than one per cell: a
half-recomputed table is a table that never existed, and undo has to
be able to say so. The header and the separator are left alone — a
formula is about data rows, and computing over the header would put a
number where the column's name goes. Rows are rebuilt at the widths
the file already used, so a recompute changes values and not layout.

* DONE Org: #+CALL and noweb references
Acceptance: =nix develop -c cargo test -p closure-eval --test noweb=

={{<<name>>}}= is what lets a literate document explain a program in

* DONE Databases: grouping
Acceptance: =nix develop -c cargo test -p closure-query --test view_groups=

=:group todo= on a view. Rendered as one org table with a rule between
groups rather than as several tables: it is one query with one set of
columns, and a reader scanning down a column should not have to
re-find it after every heading. =|---|= is an ordinary separator, so
the result is still a table Emacs will align.

extracted for the grouping and dropped again before rendering. A row
whose group value is empty keeps its own group rather than vanishing,
because hiding it would make the table disagree with the query that
produced it. Without =:group= everything is one unnamed group, so the
renderer has one shape to draw rather than two.

* DONE Databases: relations between headlines
The thing that makes a Notion database more than a saved search.

Acceptance: =nix develop -c cargo test -p closure-query --test relations=

=rel:PROJECT= as a column: the property holds another headline's id
and the column shows that headline's title. A ULID is the one string
in a vault a reader can do nothing with.

Spelled as a column rather than a new =:relation= directive, because
=:columns= already answers "what does this name mean" and a second
place to say it is how two places get out of step. It groups, so a
board of tasks by project is =:group rel:PROJECT=.

A relation that points nowhere renders =?<id>= rather than blank — a
dangling id is a mistake in the vault, and the reader has to be able
to tell it from "no project at all". And the link survives a rename,
which is the whole reason to have one instead of writing the name into
a property by hand; there is a test for exactly that.

* DONE Databases: rollups over a relation
Acceptance: =nix develop -c cargo test -p closure-query --test rollups=

=rollup:PROJECT.EFFORT:sum= — the relation to follow back, the
property to read on the rows that come back, and what to do with them.
A relation reads forwards, a rollup reads the same edge backwards and
does arithmetic on it, which is the half of a database people stare
at.

Four aggregates. Sum and count of nothing are zero, because a project
with no tasks has an effort of zero and that is a statement; min and
max of nothing are blank, because the smallest of no numbers is not
zero and saying zero would be a wrong answer rather than a missing
one. A value that is not a number is skipped rather than read as zero
— a total poisoned by one typo is worse than one that is quietly
short. An unrecognised aggregate falls back to count, the same rule an
unknown column already follows.

End to end: a table of projects with =count(EFFORT)= and =sum(EFFORT)=
beside each, and a table of tasks grouped by =rel:PROJECT=.

* DONE gpui: edit a database cell through a command
I8 — the pane mutates only through the registry.

Acceptance: =nix develop -c cargo test -p closure-shell-core --test db_edit=

The addressing is the feature, not the writing. After a filter, a sort
and a grouping, row 0 of the table is not row 0 of the vault, so the
row is resolved back to a block through the same spec that produced it
— an extra =Column::Id= on that spec rather than a second ordering
somebody has to keep in step. Writing is then an ordinary command:
=set-property=, or a rename for the title column, undoable like
everything else.

Which columns refuse is the other half. A relation shows a title and
holds an id; a rollup is arithmetic over other rows. Typing into
either writes a value the next render throws away, so both say why
instead.
